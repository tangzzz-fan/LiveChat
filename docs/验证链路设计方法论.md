## 2. 验证链路的分层模型

把「测试」拆成五层。**每一层只证明一件事**；跨层偷换结论是最常见的复盘错误。

```text
L0  正确性（功能）     消息不丢、幂等、成员校验、已读收敛
     ↑ 本仓 Phase 1：go test + 集成测试

L1  可观测性           出了问题能不能看见（metrics / 日志 / health）
     ↑ Spec 12；:8080/:8081/:8082/metrics

L2  负载行为           可控流量下延迟/吞吐/放大因子长什么样
     ↑ load_test 各场景；学习型基线

L3  故障降级           依赖坏了时，系统按设计降级还是静默躺平
     ↑ docs/chaos + scripts/chaos

L4  容量声明           「能撑多少连接 / 多少 msg/s」
     ↑ 本仓**故意不做**：本地单机证伪 Spec 01 数字；
       只证「放大因子与降级语义」
```

### 2.1 最近两轮任务落在哪一层

| 工作 | 主层 | 附带 |
|------|------|------|
| 0030 load-practice 手册 | L2 设计入口 | 指向 L3 |
| 0031 场景硬化 + 实测基线 | L2 证据 | 修假错误（OTP/限流误判） |
| 0032 发送侧背压 429 | L2→产品能力 | L3 对照（有/无背压） |
| 0033 iOS 高负载方案 | 客户端抗压设计（非容量打压） | — |
| 0026 1:1 建会话 API | L0 能力补齐 | 让 L2 不再用建群 workaround |
| 0034 protobuf 真握手 | L2 测量深度 | 让 L3 Redis 演练能看到「握手后」 |

**关键纪律**：L2 的数字**不能**直接升级成 L4 结论。本机 `connect` 98.9% 被限流，说明的是「接入限流生效」，不是「系统只能撑 5 conn/s」。

## 3. 设计原则（对外可讲的 8 条）

### P1. 先证明语义，再谈数字

先问：「积压时该不该继续收写入？」「Redis 挂了消息还在不在？」  
数字（P95、req/s）是**佐证**，不是目标本身。

### P2. 放大因子优先于单接口 QPS

IM 里一次用户动作常变成：1 message + 1 outbox + N sync_events + 路由查找 + 可选推送。  
场景设计应显式写出放大式，例如：

```text
群消息: 1 send → 1 outbox → N sync_events（N = 成员数）
```

### P3. 区分「保护生效」与「系统故障」

| 现象 | 正确归类 |
|------|----------|
| Gateway 429 / upgrade 被拒 | 接入限流**按设计工作** |
| send 429 + `Retry-After` | 背压**按设计工作** |
| 5xx、丢消息、数据损坏 | 故障 |
| 握手成功但收不到投递 | **静默降级**（比 5xx 更危险，要单独记） |

### P4. 每个场景只设一个主问题

反例：一个场景同时测吞吐、重连、热点群、DB 宕机 → 结果不可解释。  
正例：`realtime_delivery` 只问「对端 WebSocket 是否收到」。

### P5. 对照实验优于单点数字

| 好对照 | 说明什么 |
|--------|----------|
| jitter vs no-jitter | 客户端退避是否改变恢复成功率 |
| 有背压 vs 无背压（consumer 暂停） | pending 是否被封顶 |
| Redis 中断前后：握手 / 投递 / 补拉 | 各层依赖边界 |

### P6. 测量深度必须匹配声称深度

| 声称 | 最低测量深度 |
|------|----------------|
| 「能建连」 | HTTP upgrade |
| 「在线可达」 | protobuf 握手 + 路由注册后的投递 |
| 「消息不丢」 | 故障期间写入 + 恢复后 sync/补拉 |
| 「实时投递」 | 对端收到 `MESSAGE_DELIVERY`，不是 send 200 |

0034 之前只测到 upgrade，却容易口头滑向「在线可达」——这是测量深度不够。

### P7. 演练工具本身也是验证对象

本轮修过的坑都属此类：

- `pgrep -f` 停到 shell 包装进程 → 演练「看起来注入了」其实没注入  
- health-check 把标签当命令 → 全绿/全红都不可信  
- 每次迭代注册新用户 → OTP 频控制造假错误率  

**原则**：注入脚本、health-check、压测客户端，和被测系统同等重要。

### P8. 明确「不宣称」清单（学习型项目的诚实边界）

本仓对外应主动说：

- **不**宣称达到 Spec 01 的 5 万–20 万连接  
- **不**用单 IP 本机吞吐外推容量  
- **不**用 iOS 模拟器打服务端容量  
- 容量验证 = **放大因子与降级语义的本地实证**

## 4. 如何设计一个场景（必要内容 checklist）

新场景上线前，下面 8 项应能填完。填不完 = 场景不成熟。

| # | 必要项 | 问自己 | 本仓落点示例 |
|---|--------|--------|--------------|
| 1 | **主问题** | 一句话：这次要证伪/证实什么？ | 「Outbox 停了，send 是否应无限写入？」 |
| 2 | **放大因子** | 1 次动作变成几次写/几次 RPC？ | 群扇出 ×N |
| 3 | **注入或负载方式** | 流量怎么来？故障怎么来？ | `run.py --scenario` / `chaos/*.sh` |
| 4 | **主信号** | 看哪个指标才算「答到了主问题」？ | `send_backpressure_rejected_total`、pending |
| 5 | **反信号** | 什么看起来像失败其实不是？ | connect 的 throttled ≠ Errors |
| 6 | **通过标准** | 学习型：方向对 + 可恢复；非绝对 QPS | pending 封顶后恢复能放行 |
| 7 | **恢复路径** | 怎么回到干净状态？ | `*-resume.sh` + health-check |
| 8 | **不考察清单** | 明确写出本场景不证明什么 | `reconnect_storm` 不证明业务吞吐 |

### 4.1 场景模板（可直接套）

```markdown
## 主问题
...

## 放大因子
...

## 如何制造压力 / 故障
...

## 预期系统行为
1. ...
2. ...

## 主信号 / 反信号
| 信号 | 预期 | 反信号（勿误判） |
|------|------|------------------|

## 通过标准
- [ ] ...

## 本场景不证明
- ...
```

`docs/load-practice/` 与 `docs/chaos/` 的手册大体遵循这个骨架；新场景应继续对齐。

## 5. 本仓场景一览：考察什么 / 不考察什么

### 5.1 压测场景（`load_test/`）

| 场景 | 主问题 | 主信号 | 不考察 |
|------|--------|--------|--------|
| `send_message` | 写路径在可控并发下是否稳定 | 吞吐、P95、5xx≈0；可出现受控 429 | 对端是否实时收到 |
| `connect` | 建连路径与接入限流是否按设计工作 | `handshake_ok` vs `upgrade_throttled` | 连接容量绝对值 |
| `realtime_delivery` | 在线投递链路是否真通 | 投递率、端到端 P50/P95 | 纯网络 RTT（含 outbox+扇出） |
| `group_fanout` | 写扩散是否随成员数放大 | 延迟随 N 上升；可触达热点保护 | 「群能撑多大」的产品承诺 |
| `sync_backfill` | 游标落后时补拉是否可用 | 分页延迟、错误率 | 多端并发游标竞争细节 |
| `reconnect_storm` | 同步重连是否需要 jitter | 有/无 jitter 的重连成功率 | execute 阶段的 rps（空转） |

### 5.2 混沌场景（`docs/chaos/`）

| 场景 | 主问题 | 主信号 | 典型误判 |
|------|--------|--------|----------|
| 01 Redis 不可用 | 实时路径依赖 Redis，耐久路径是否不依赖 | send 仍 200；补拉齐全；**握手成功但投递停** | 「握手成功 = 在线」 |
| 02 Outbox 暂停 | 积压时有无发送侧保护 | 有背压：429 + pending 封顶；无背压：pending 无限涨 | 把 429 当故障 |
| 03 DB 暂停 | 写入权威不可用时的失败面 | send 失败面清晰；恢复后一致 | — |
| 04 Push 延迟 | 推送不是真相路径 | sync 仍可达 | 把推送当消息投递 |
| 05 Gateway kill | 连接断开后客户端能否恢复 | 重连 + 补拉 | 单机无法证多节点导流 |
| 06 热点群 | 写扩散保护是否触发 | `ErrGroupBusy` / 不重试 | 用成员数当阈值（实际是 60s 消息数） |

### 5.3 「必要内容」最小集合（没有就不可信）

对「高负载 IM 验证」这一叙事，最小可信集合是：

1. **写路径场景**（send）— 系统能写  
2. **在线投递场景**（realtime_delivery）— 不只是能写  
3. **至少一种积压/背压对照**（chaos 02 + 0032）— 会自我保护  
4. **至少一种依赖故障**（chaos 01 Redis）— 知道依赖边界  
5. **一份写明「不宣称容量」的基线** — 防止数字被误读  
6. **可重复的注入/恢复脚本 + health-check** — 否则演练不可复现  

0034 补上第 2 项之前，第 2 项是假齐全（只有 upgrade）。

## 6. 对外怎么讲：最近两轮任务的叙事脚本

下面三段可直接用于复盘分享 / 面试项目介绍。每段都带**证据落点**。

### 叙事 A — 「我们不是在刷 QPS，是在验证放大因子」

> 学习型 IM 的容量假设（连接数、msg/s）在单机无法实证。我们把目标改成：用可控流量把**放大因子**和**降级语义**打出来。  
> 例如：群消息 1 写变 N 条 sync；重连无 jitter 时恢复成功率归零。  
> 证据：[`高负载IM验证计划.md`](./高负载IM验证计划.md)、[`local-measured-baseline.md`](../load_test/baselines/local-measured-baseline.md)

### 叙事 B — 「保护生效曾被误当成故障」

> 早期 connect 场景显示 87%～99%「错误」。拆开后发现两类假信号：OTP 同 IP 频控、Gateway 每 IP 5 conn/s 限流。  
> 我们把结果改成三态：`handshake_ok` / `handshake_rejected` / `upgrade_throttled`。  
> 对外结论变成：限流按设计工作；单 IP 压测不能外推连接容量。  
> 证据：issue 0031/0034、`load_test/scenarios/connect.py`

### 叙事 C — 「测量深度不够会得出错觉」

> 只验证 WebSocket upgrade，会以为「连上了」。补上 protobuf 握手与 `MESSAGE_DELIVERY` 后才发现：  
> Redis 中断时握手仍成功，但既有连接收不到投递——静默降级。  
> 另一侧：有背压时 consumer 暂停，send 95% 返回 429，pending 封顶；恢复后自动放行。  
> 证据：[chaos 01](./chaos/01-redis-outage.md)、[chaos 02](./chaos/02-outbox-backpressure.md)、`realtime_delivery` 场景

### 30 秒电梯稿

> 我们给学习型 WhatsApp 类系统设计了一套验证链：正确性测试 → 压测场景 → 混沌注入。  
> 不追求打满容量数字，而追求证明：写扩散会放大、限流与背压会保护、依赖故障时消息仍可补拉、以及「握手成功≠在线可达」这类静默降级。  
> 证据落在 load-practice、chaos 手册和本机实测基线里。

## 9. 开放缺口（诚实清单）

| 缺口 | 影响 | 建议 |
|------|------|------|
| 多机 / 多 IP 压测 | 无法绕过单 IP 接入限流谈连接容量 | 明确保持「不宣称」 |
| Gateway 多节点 failover | chaos 05 只能证重连，不能证导流 | 等多实例部署 |
| 投递场景按 `client_message_id` 精确配对 | 当前是共享队列近似延迟 | 需要时再加强 |
| 服务端路由注册失败无降级信号 | 客户端只能靠超时/补拉发现静默降级 | 可作为后续票 |
| 热点群 `ErrGroupBusy` 本轮未专门抬成员数打出 | 手册有、实测弱 | 一次专项演练即可补 |
