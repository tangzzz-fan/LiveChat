# LiveChat：仓库现状与商用品差距

> 学习闭环收口后的阶段性快照（issues 0001–0064 无开放票）。  
> 对照阅读：[`架构设计总览.md`](./架构设计总览.md) · [`ios-client-study-guide.md`](./ios-client-study-guide.md) · [`Specs/00-规格总览与实施规划.md`](../Specs/00-规格总览与实施规划.md)

**定位一句话**：本仓是规格驱动的 WhatsApp **类** IM **学习系统**——把正确性、同步、扇出、弱网、可观测等问题做「可演示、可压测、可复盘」；**不是**面向 SLA / 合规 / 全球分发的商用 IM 产品。

---

## 1. 当前仓库状态总结

### 1.1 已闭环的能力层

| 层 | 位置 | 完成度（学习闭环） |
|----|------|-------------------|
| 规格 | `Specs/00–13` | 设计源齐全：生命周期 → Outbox → 网关 → 同步 → 群/媒体/推送 → 安全/存储/压测 → iOS |
| 服务端 | `livechat-server/` | Phase 1–3：1:1/群、幂等发送、实时投递、增量 sync、已读、图片、认证设备、推送编排、背压、压测/混沌配套 |
| iOS | `ios/` SPM 四包 + 薄 App | 重写完成：本地优先、GRDB 投影、WS、sync/缺口补拉、图片、已读未读、取消发送、长按/多选/转发分享、一批 UX 修复 |
| 验证资产 | `load_test/`、`docs/chaos/`、`docs/engineering-problems/` | 有场景、手册与问题库，便于学习与回归叙事 |

默认运行时依赖为本机 **PostgreSQL + Redis**；三个长驻进程：`message-service` / `gateway` / `outbox-consumer`。

### 1.2 Issue 账本

- **0001–0064**：无 `ready-for-agent` / `in-progress`。
- 早期 iOS 票 **0022–0025、0027–0028** 为 `superseded→0035`（由 SPM 重写替代）。
- **刻意暂缓**：已发消息编辑（0059 / ADR 0005）——缺服务端事件模型，不实现。
- Spec 13 仍列出、**未拆票**的 P1：NSE 解密、E2EE、视频转码/审核。
- study-guide 中的 ⚠️（如 `delivered` ACK、WS 状态帧、token 静默 refresh）属**已知技术债**，不是开放功能票。

### 1.3 产品视角：现在能演示什么

**主路径可联调**：OTP 登录 → 建 1:1 → 文本/图片本地优先发送 → 实时或离线补齐 → 会话列表与未读 → 已读 → 弱网队列/取消发送 → 复制/本地删除/多选/转发/系统分享。

**明确不在当前闭环**：消息编辑、真 E2EE、NSE 解密预览、视频管线；iOS 群聊 UI/完整体验相对服务端群能力仍偏「服务端已有、客户端未作为产品重点」。

### 1.4 阶段位置

按能力闭环：**服务端 Phase 1–3 + 高负载验证 + iOS 重写与交互票均已收口**。仓库处于「主链路可联调、开放票清空」。下一步应是新 Phase 拆票（编辑协议、群客户端、E2EE 等），而不是补遗留半成品功能。

> 注：`CLAUDE.md` 中「Phase 2 尚未开始」等表述可能滞后；以本文件与 `issues/INDEX.md` 为准。

## 2. 与商用 IM 的差距（总览）

商用对照物取 **WhatsApp / 企业微信 / 大型消费级 IM** 的共性门槛，而不是某一家的全部功能清单。差距按「学习已覆盖骨架」vs「商用还要补的厚度」来写。

```text
本仓已覆盖（骨架）          商用还要补的厚度
─────────────────          ─────────────────
消息生命周期 / 幂等         全球多活、强 SLA、容量承诺
Outbox + 扇出模型           分片、热点隔离、成本优化到极致
长连接 + 增量 sync          亿级连接、运营商网络适配、灰度/容灾
OTP + 设备会话              风控、实名、反作弊、账号体系产品化
图片直传（学习存储）        CDN、转码、审核、版权、多码率
压测/混沌手册               7×24 SRE、on-call、真实故障预算
iOS 本地优先 Demo App       多端一致体验、无障碍、增长与合规
```

一句话：**本仓证明「怎么做对」；商用要证明「怎么在真实流量、真实监管、真实组织下长期做对且赚钱」。**

## 3. 分维度差距

### 3.1 产品与用户体验

| 维度 | 本仓 | 典型商用 |
|------|------|----------|
| 对话形态 | 1:1 主路径清晰；群以服务端/规格为主 | 群/频道/社区、@、回复引用、表情回应、语音、通话入口 |
| 消息能力 | 文本 + 图片；转发=内容等价新发 | 引用回复、编辑/撤回（协议完备）、语音、视频、文件、位置、名片等 |
| 联系人与发现 | 按 user_id / OTP 学习路径 | 通讯录哈希匹配、推荐、隐私开关、企业通讯录 |
| 多端 | 规格与部分服务端能力；iOS 单端 Demo | iOS/Android/Desktop/Web 功能对齐与冲突策略产品化 |
| UI/UX | 学习用最小聊天壳 | 设计系统、无障碍、国际化、暗色、性能感知体验 |
| 增长与运营 | 无 | Push 营销合规、活动、客服、审核后台 |

### 3.2 协议与正确性厚度

| 维度 | 本仓 | 典型商用 |
|------|------|----------|
| 幂等 / seq / sync | 主链路具备，可演示 | 同样思想，但边界 case、版本演进、兼容窗口更长 |
| 回执 | 已读路径可用；`delivered` 等仍有缺口 | delivered/read/播放进度等状态机完整且可观测 |
| 编辑 / 撤回 | 编辑暂缓；本地删除≠服务端撤回 | 服务端事件 + 全端投影 + 审计 |
| E2EE | Spec/P1 预留，未全量实现 | 消费级 IM 常为卖点或合规要求；密钥生命周期、备份、多设备配对 |
| 推送内容 | Token + 静默唤醒学习路径 | NSE/解密预览、折叠、优先级、厂商通道差异 |

### 3.3 媒体与内容安全

| 维度 | 本仓 | 典型商用 |
|------|------|----------|
| 存储 | 学习向本地/简单对象路径 | 多区域对象存储 + CDN + 生命周期归档 |
| 图片 | 上传/授权下载/缩略展示 | 多尺寸、渐进加载、EXIF 策略、防盗链 |
| 视频/文件 | 明确非 P0 | 转码管线、分片上传、断点续传、容量配额 |
| 审核 | 未做 | 涉政涉黄自动审 + 人工审 + 举报闭环 |

### 3.4 基础设施与可靠性

| 维度 | 本仓 | 典型商用 |
|------|------|----------|
| 部署形态 | 本机三进程 + 单机 PG/Redis | K8s/多 AZ、配置中心、密钥托管、蓝绿/金丝雀 |
| 存储分层 | 规格与学习实现 | 热冷温、分片键、跨区复制、备份 RPO/RTO |
| 容量 | 有压测框架与学习基线 | 容量模型、限流分层、成本账单、峰值预案 |
| 可观测 | Histogram/追踪/告警规则学习闭环 | 全链路 SLO 看板、错误预算、on-call 轮值 |
| 安全合规 | 安全基线学习向 | SOC2/等保、渗透、密钥轮换、DLP、审计留存年限 |

### 3.5 客户端工程化

| 维度 | 本仓 | 典型商用 |
|------|------|----------|
| 架构 | SPM + Redux + GRDB，边界清晰 | 同类思想 + 更大模块联邦、Feature Flag、实验平台 |
| SDK 拆分 | 有 Core vs UI 讨论文档 | 对外 SDK、版本兼容、多 App 复用 |
| 质量 | 包级单测 + 联调手册 | UI 自动化、设备农场、灰度、崩溃率 KPI |
| 发布 | 学习工程 | 证书、渠道包、热修、强制升级策略 |

### 3.6 组织与商业

商用差距里常被低估、但最「硬」的部分：

- **SLA 与合同**：可用性、数据驻留、企业功能计费  
- **法务与隐私**：隐私政策、用户数据导出/删除、未成年人保护  
- **运营体系**：客服、封禁、申诉、内容治理人力  
- **多团队协作**：协议兼容窗口、跨端发布火车、事故复盘文化  

本仓刻意不模拟这些组织成本。

## 4. 「差距」不等于「失败」——本仓已经对齐的商用思想

下列能力在思想上与商用同构，差异主要在**规模、完整度和组织配套**：

1. **单一可信状态源**：服务端事件 + 客户端本地投影，而不是 UI 各自发明状态。  
2. **本地优先发送 + 幂等 `client_message_id`**。  
3. **Outbox / 异步扇出**，接入层与业务语义分离。  
4. **会话内序号与离线增量游标分层**（不全混用一个序号）。  
5. **弱网：队列、超时收回、path 恢复、取消发送**。  
6. **压测与混沌当作规格的一部分**，而不是上线后补课。

因此面试/复盘叙事应强调：**学会的是工业级问题分解与边界**，而不是「已经做出一个 WhatsApp」。

## 5. 若要以商用为目标：建议优先级（非承诺排期）

仅作路线图参考；真正开工仍应按仓库惯例 **先改 Spec → 拆 ticket → 再实现**。

| 优先级 | 方向 | 为何接近商用 |
|--------|------|----------------|
| P0 | 补齐回执/WS 状态帧、token 刷新等 study-guide ⚠️ | 正确性与多端观感 |
| P0 | 群聊 iOS 闭环（列表/成员/发消息） | 用户可感知能力对齐服务端 |
| P1 | 消息编辑/撤回（先定 ADR 事件模型） | 基础消息产品能力 |
| P1 | 媒体：CDN 形态、视频/文件最小管线 | 内容形态接近消费级 |
| P2 | E2EE + NSE 预览 | 安全卖点与规格 P1 |
| P2 | 多活/分片/正式 SRE 体系 | 规模化，而非功能点 |
